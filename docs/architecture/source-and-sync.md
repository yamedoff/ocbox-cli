# CLI source delivery and local transfer recovery

## What it does

Every hosted push answer carries `phases: [{phase, ms}]`: one entry per progress event in the order it ran (`scan`, `check`, `prepared`, `plan`, `upload`, `apply`, `complete`), with `ms` the whole time from that event to the next and the last running to the end of the push. A phase that runs twice appears twice; the human renderer ignores the field.

Every hosted push uses the content-addressed v2 transport for a mapped `sesdo_` Session. On a v3 box a push with no local change first asks the terminal check whether the box already holds the local tree: an unchanged answer prints `Source unchanged.` and stops. A small local delta with previous state and no deleted paths goes straight to the fast apply: `applied` finishes the push, and `changed` makes the CLI run the check it skipped and report the same conflict. A delta that deletes a synced path keeps the check first, then takes the fast apply or v2 as today. Anything else keeps the check-then-v2 cycle, and a server without the v3 routes falls back to v2. Hosted diff and pull reuse the same CAS v2 box: a fresh snapshot describes the box tree, diff compares it with the local tree, and pull downloads the changed files and writes them atomically. The fake/local validation path also has a two-sided manifest planner and journalled filesystem transfer. These paths have different capabilities and must not be described interchangeably.

## Inside

scanSourceManifest applies ignore groups, normalizes safe paths and hashes file contents. There is no archive or manifest/chunk upload route in the CLI: the retired hosted source upload was removed, so a hosted Session without a CAS transport refuses the push instead of falling back to an archive.

The local transfer adapter stages files, records a durable intent, moves/replaces the target and updates the verified baseline under a lock. Recovery never promotes staged content and never deletes an ambiguous backup; it restores the original target or its proven absence.

V2 resolves the owned running sandbox mapping before building its transport. runCasPush applies the same safe scan and excludes the state subtree before reading it. buildCasSnapshot preserves verified unchanged bundle slices, packs initial small files into 8 MiB bundles and splits large files into 16 MiB parts. With previous state and at most 512 dirty files in total, dirty small files become individual blobs. Canonical object-key sorting hashes each bounded manifest page.

The v3 check sends a SHA-256 fingerprint of the path-ordered tree (files as path/hash/size/mode, directories as path) and, when it fits, the local changed paths. The fingerprint is identical to the server's `casTreeFingerprint`; it leaves out the random sync identity, pages and blob parts. The check is read-only, so an unchanged answer neither plans nor mutates state. A push with no local change, or with no previous state, keeps the check; a local delta with previous state and no deleted paths that is one request (at most 512 changed entries, 1,024 deleted paths, 4,096 blobs and 512 KiB plus 32 KiB) skips it, and `fastApplyCasSnapshot` sends only the changed files, their blobs and the deleted paths. A delta that deletes a synced path keeps the check first, then takes the same fast apply or v2 cycle. The server answers `awaiting_blobs` until the store has every blob, then `applied`; the same request key is replayed throughout. A `changed` answer means an agent edited an owned path the delta does not name: it applies nothing, names the edited paths, and the CLI then runs the check it skipped and reports the same conflict as the check-then-fast-apply flow. A `manifest_invalid` refusal (a box with no applied record) or a missing route falls back to the full v2 cycle instead of failing the push.

syncCasSnapshot plans each page, validates every requested blob against that page, and uploads through opaque capabilities with four workers. PUTs omit API credentials and reject redirects. createCasTransport uses the normal authenticated generated client for plan/apply; only safe categories enter typed errors. Apply replays the same key until a matching terminal receipt. Plan/apply control calls and capability PUTs use separate connections; the upload endpoint is opaque. Each PUT has a 120-second timer and retries transient failures after 1 then 2 seconds.

Hosted read-back uses the same transport for snapshot, snapshot-page and pull control calls. `runSyncDiff` always refreshes, replays a pending snapshot with the same idempotency key, reads the remaining immutable pages, validates them against the snapshot manifest, and compares file size/SHA-256 with the local scan. `runHostedPull` requests the changed files, replays a pending pull until terminal, follows `nextCursor` across GET-capability pages, verifies every part blob and reassembled file hash, and renames verified temporary files into place. It creates added directories and removes local-only paths only after `--delete` approval. Download capabilities are opaque URLs; the CLI rejects redirects, credentials and non-loopback cleartext, and never attaches its API bearer.

## Data it keeps

Source manifests, verified baselines, local transfer journals and hosted receipt/operation IDs. V2 keeps unsigned pending/success metadata and cached source blobs in an API/Session/root-scoped local state directory; URLs and credentials are never persisted there. The v3 fingerprint is recomputed from the current tree on every push and is never trusted from the local success file. Every invocation rehashes source and verifies cache content. Hosted push does not claim that a local baseline proves the remote workspace is unchanged.

V2 metadata and blobs are written via exclusive 0600 temporary files and rename; directory creation requests 0700. These writers do not fsync or verify Windows ACLs. Source is rehashed on each invocation, and reusable cached slices are checked by size and SHA-256.

## States

V3: scan/fingerprint → no local delta or no previous state: check → (unchanged | v2); small local delta with previous state and no deleted paths: fast apply/PUT/replay → (applied → save success | changed → check → conflict); local delta that deletes a synced path: check → (unchanged | fast apply or v2); other local delta: check → (unchanged | v2). V2: scan → pack → save pending → plan/PUT → apply/poll → save success. A retry reuses a pending identity only for matching page hashes younger than 45 minutes; terminal refusals clear it. Local: plan → staged → target-moving → target-moved → committed, with explicit recovery gates. A pending journal blocks another local transfer.

## Limits and config

V3: at most one check per push with up to 1,024 changed paths in the request (a small local delta with no deleted paths skips it unless the fast apply answers `changed`; a delta that deletes a synced path keeps it); the fast delta is at most 512 entries, 1,024 deleted paths, 4,096 blobs and one request under 512 KiB plus 32 KiB, replayed until terminal within the same 15-minute apply deadline. V2: 100,000 entries, 1 GiB total, 256 MiB per file, 4,096 blobs; pages have 512 entries/512 KiB, at most 512 pages/32 MiB metadata. PUTs have 3 attempts/120-second timers; apply checks a 15-minute loop deadline before each request and polls pending receipts after up to 1 second. Control calls/body reads have separate authenticated transport timers, so 15 minutes is not a hard end-to-end wall-clock cap. Apply wait defaults to 5 minutes with a 1-second healthy polling interval.

## When it fails

Hosted recover is refused when its capability is absent; a hosted server without the pull route answers `Server does not support sync pull yet`, and a server without snapshots answers `Server does not support source snapshots yet`. A server without the v3 check or fast route falls back to the v2 push; a fast apply refused for a missing applied record does the same. A fast apply that answers `changed` runs the skipped check and reports the same conflict. A failed check or fast apply does not change the v2 error categories. A hosted push without a CAS transport is refused as unsupported. V2 removal of paths from the local success state requires --delete and confirmation/--yes; it is not a cross-machine conflict check. A hosted pull hash mismatch leaves the target file untouched. Server conflicts, invalid receipts and integrity errors fail safely; interruption preserves unsigned resume state. Local deletion requires --delete and explicit confirmation/--yes. Unsafe paths, sensitive material, checksum mismatch, conflicts and incomplete recovery fail without a force/replace bypass.
