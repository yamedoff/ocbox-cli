# CLI source delivery and local transfer recovery

## What it does
Hosted push selects content-addressed v2 for a mapped `sesdo_` Session and manifest/chunk/checksum calls for older Sessions. On a v3 box it first asks the terminal check whether the box already holds the local tree: an unchanged answer prints `Source unchanged.` and stops, a small local delta takes the fast apply, and anything else uses the full v2 cycle. A server without the v3 routes falls back to v2. Hosted diff and pull reuse the same CAS v2 box: a fresh snapshot describes the box tree, diff compares it with the local tree, and pull downloads the changed files and writes them atomically. The fake/local validation path also has a two-sided manifest planner and journalled filesystem transfer. These paths have different capabilities and must not be described interchangeably.

## Inside
scanSourceManifest applies ignore groups, normalizes safe paths and hashes file contents. Legacy hosted push refuses remote deletion, builds a bounded archive and calls uploadPreparedSource. The upload derives idempotency keys from content, Session and predecessor receipt lineage; an A→B→A change cannot incorrectly reuse A's old successful delivery.

Each chunk is SHA-256 verified. A conflicting upload succeeds only when the server receipt has the same checksum. After verifySourceChecksum returns an operation, the client polls and re-verifies the terminal receipt. Success requires the correct manifest ID, checksum and chunk count.

The local transfer adapter stages files, records a durable intent, moves/replaces the target and updates the verified baseline under a lock. Recovery never promotes staged content and never deletes an ambiguous backup; it restores the original target or its proven absence.

V2 resolves the owned running sandbox mapping before building its transport. runCasPush applies the same safe scan and excludes the state subtree before reading it. buildCasSnapshot preserves verified unchanged bundle slices, packs initial small files into 8 MiB bundles and splits large files into 16 MiB parts. With previous state and at most 512 dirty files in total, dirty small files become individual blobs. Canonical object-key sorting hashes each bounded manifest page.

The v3 check sends a SHA-256 fingerprint of the path-ordered tree (files as path/hash/size/mode, directories as path) and, when it fits, the local changed paths. The fingerprint is identical to the server's `casTreeFingerprint`; it leaves out the random sync identity, pages and blob parts. The check is read-only, so an unchanged answer neither plans nor mutates state. When the check reports a change and the local delta is one request (at most 512 changed entries, 1,024 deleted paths, 4,096 blobs and 512 KiB plus 32 KiB), `fastApplyCasSnapshot` sends only the changed files, their blobs and the deleted paths. The server answers `awaiting_blobs` until the store has every blob, then `applied`; the same request key is replayed throughout. A `manifest_invalid` refusal (a box with no applied record) or a missing route falls back to the full v2 cycle instead of failing the push.

syncCasSnapshot plans each page, validates every requested blob against that page, and uploads through opaque capabilities with four workers. PUTs omit API credentials and reject redirects. createCasTransport uses the normal authenticated generated client for plan/apply; only safe categories enter typed errors. Apply replays the same key until a matching terminal receipt. Plan/apply control calls and capability PUTs use separate connections; the upload endpoint is opaque. Each PUT has a 120-second timer and retries transient failures after 1 then 2 seconds.

Hosted read-back uses the same transport for snapshot, snapshot-page and pull control calls. `runSyncDiff` always refreshes, replays a pending snapshot with the same idempotency key, reads the remaining immutable pages, validates them against the snapshot manifest, and compares file size/SHA-256 with the local scan. `runHostedPull` requests the changed files, replays a pending pull until terminal, follows `nextCursor` across GET-capability pages, verifies every part blob and reassembled file hash, and renames verified temporary files into place. It creates added directories and removes local-only paths only after `--delete` approval. Download capabilities are opaque URLs; the CLI rejects redirects, credentials and non-loopback cleartext, and never attaches its API bearer.

## Data it keeps
Source manifests, verified baselines, local transfer journals and hosted receipt/operation IDs. V2 keeps unsigned pending/success metadata and cached source blobs in an API/Session/root-scoped local state directory; URLs and credentials are never persisted there. The v3 fingerprint is recomputed from the current tree on every push and is never trusted from the local success file. Every invocation rehashes source and verifies cache content. Hosted push does not claim that a local baseline proves the remote workspace is unchanged.

V2 metadata and blobs are written via exclusive 0600 temporary files and rename; directory creation requests 0700. These writers do not fsync or verify Windows ACLs. Source is rehashed on each invocation, and reusable cached slices are checked by size and SHA-256.

## States
V3: scan/fingerprint → check → (unchanged | fast apply/PUT/replay → save success | v2). V2: scan → pack → save pending → plan/PUT → apply/poll → save success. A retry reuses a pending identity only for matching page hashes younger than 45 minutes; terminal refusals clear it. Legacy hosted: safe scan → archive → manifest → chunks → verification/apply → matching receipt. Local: plan → staged → target-moving → target-moved → committed, with explicit recovery gates. A pending journal blocks another local transfer.

## Limits and config
V3: one check per push with up to 1,024 changed paths in the request; the fast delta is at most 512 entries, 1,024 deleted paths, 4,096 blobs and one request under 512 KiB plus 32 KiB, replayed until terminal within the same 15-minute apply deadline. V2: 100,000 entries, 1 GiB total, 256 MiB per file, 4,096 blobs; pages have 512 entries/512 KiB, at most 512 pages/32 MiB metadata. PUTs have 3 attempts/120-second timers; apply checks a 15-minute loop deadline before each request and polls pending receipts after up to 1 second. Control calls/body reads have separate authenticated transport timers, so 15 minutes is not a hard end-to-end wall-clock cap. Legacy hosted source: 100 files, 64 KiB per file, 512 KiB total content, 1 MiB archive. Chunks default to 256 KiB; retryable chunk failures have at most 3 attempts. Receipt listing allows at most 100 pages and rejects repeated cursors. Apply wait defaults to 5 minutes with a 1-second healthy polling interval.

## When it fails
Hosted recover is refused when its capability is absent; a hosted server without the pull route answers `Server does not support sync pull yet`, and a server without snapshots answers `Server does not support source snapshots yet`. A server without the v3 check or fast route falls back to the v2 push; a fast apply refused for a missing applied record does the same. A failed check or fast apply does not change the v2 error categories. Legacy hosted push with --delete is unsupported. V2 removal of paths from the local success state requires --delete and confirmation/--yes; it is not a cross-machine conflict check. A hosted pull hash mismatch leaves the target file untouched. Server conflicts, invalid receipts and integrity errors fail safely; interruption preserves unsigned resume state. Local deletion requires --delete and explicit confirmation/--yes. Unsafe paths, sensitive material, checksum mismatch, conflicts and incomplete recovery fail without a force/replace bypass.
